# SiliconDraft 需求文档评审：需求（What）与实现（How）的分离

> **评审对象**：`doc/requirements-merged.MD`（v1.0 合并版，4988 行 / 17 章）
> **评审问题**：需求文档应聚焦"做什么"（功能目标、业务规则、输入输出、验收标准），"如何做"（技术选型、数据结构、接口签名、算法步骤）应移出或单独归档。本文档给出**识别结果**、**处置建议**与**目标结构**。
> **评审日期**：2026-10-14
> **结论**：现状是一份"需求 + 设计 + 契约 + 流程"四合一文档。建议拆分为**三册**，其中**约 2500 行（≈50%）应移出需求正文**。

### 1.2 三个最严重的问题

**问题一：技术选型被写成"冻结决策"，把需求文档的有效期绑死在技术上**

§0.5 的 `D-01`（全 .NET / C#）、`D-03`（Avalonia 12）、`D-04`（OxyPlot + SkiaSharp 自绘）、`D-16`（DuckDB）、`D-17`（AssemblyLoadContext 插件机制）被列为"MUST 级冻结决策，不要再重新提出"。后果：

- 换 UI 框架、换存储引擎、换图表库 **都要修改需求文档**——而需求文档本应在技术选型变化时保持稳定。
- §1.1、§16.2 又用两张表把这些选型重复一遍，形成**三处真相**。

**问题二：内部实现被编号为 MUST 需求，使"实现方式"成为"验收对象"**

| 被写成需求的东西 | 位置 | 后果 |
| --- | --- | --- |
| C# 接口签名（`IConnectionManager`、`IExportPlugin`、`IDataCursor`、`ExportContext`） | §4.4、§6.3 | 任何签名重构都"违反需求"，必须走需求变更流程 |
| 数据库表结构与字段（34 张 `CREATE TABLE`） | §4.2、§16.10 | 表设计成为验收项，DDL 优化被迫走需求评审 |
| 锁文件字段（`pid`/`host`/`heartbeatAt`/`appProcessStartTicks`） | §2.6 | 实现机制细节固化 |
| `SemaphoreSlim(1,1)`、`AssemblyLoadContext`、`File.Move` 原子替换 | §2.6、§6.4、§5.4 | 具体 API 进入需求正文 |
| `Program.cs` 的 `Main` 分支逻辑 | §1.4 | 代码骨架成为需求 |

**问题三：对外契约与内部实现平级混排，读者无法区分"改它会不会破坏外部系统"**

- **对外契约**（外部系统依赖，改动 = 破坏性变更）：CLI 命令/参数/退出码、配置文件字段、STDF/AD5 输出格式、日志字段。→ **应保留在需求侧并显式标记为"稳定契约"**。
- **内部实现**（可自由重构）：C# 接口、表结构、目录内部布局、ALC 机制。→ **应移出**。

现状下两者混在同一章节体系里（如 §8.2 的"命令集"与"实现技术栈"相邻），读者无法快速判断。

### 1.3 一句话结论

> **拆成三册**：`需求规格（What）` + `技术设计（How）` + `接口与格式规格（Contract）`。契约类内容保留在需求侧或独立成册，内部实现全部移出。

### 2.2 三个容易误判的边界（本次评审采用的判定）

**边界一：CLI 命令与退出码 ≠ 实现细节**

它们是**对外契约**——CI 流水线、调度系统、外部 YMS 测试框架直接依赖。删掉它们，需求文档就无法回答"外部系统怎么调用我"。**应保留，并显式标注"契约稳定，破坏性变更需公告"**。
但"用 `System.CommandLine` 还是 `Spectre.Console` 解析"是**实现**。

**边界二："技术约束" ≠ "技术选型"**

| 表述 | 判定 | 理由 |
| --- | --- | --- |
| "必须支持 Windows / macOS / Linux 三平台对等" | ✅ 需求 | 对能力的要求，不指定用什么实现 |
| "运行时基线为 .NET 10 (LTS)" | ❌ 实现 | 指定了技术选型 |
| "产品不得依赖 Python 运行时" | ✅ 需求 | 部署环境的硬约束 |
| "必须使用 `BinaryPrimitives` 而非 `BitConverter`" | ❌ 实现 | 指定了实现手段 |
| "GUI 不得监听网络端口、不得暴露远程访问面" | ✅ 需求 | 安全约束与部署形态要求 |
| "GUI 用 Avalonia 12 + CommunityToolkit.Mvvm" | ❌ 实现 | 指定了框架 |

**边界三：工作簿目录包 = 契约，不是纯内部实现**

用户会**拷贝、分发、跨机器打开**工作簿（`D-07`/`D-08`/`SD-SYS-246`）。因此：
- "工作簿必须是自包含、可重定位、跨平台可直接拷贝打开的目录包" → ✅ **需求**
- "目录内有哪些文件、`workbook.json` 有哪些字段、`checksums` 何时写入" → ❌ **格式规格**（移入契约册）

## 五、建议的文档体系（三册）

```
doc/
├── requirements.md              ← 需求规格说明书（What）—— 本册聚焦"做什么"
├── design.md                    ← 技术设计说明书（How）—— 承接移出的全部实现细节
├── contracts/                   ← 接口与格式规格（Contract）—— 对外 / 对工具的稳定契约
│   ├── cli.md                   ←   命令、参数、退出码、日志字段、环境变量
│   ├── config.md                ←   配置项参考（字段、类型、默认值、约束）
│   ├── workbook-package.md      ←   工作簿目录包与清单文件规范
│   ├── plugin.md                ←   插件清单与契约程序集规范
│   └── formats/
│       ├── stdf.md              ←   STDF 输出规格（记录、字段映射、profile）
│       └── ad5.md               ←   AD5 输出规格（待冻结）
└── (历史归档：requirements.MD / requirements-v2.MD / requirements-v3.MD)
```

**为什么把"契约"独立成册而不是并入设计册**：契约是**双向**的——内部实现依赖它，外部系统也依赖它。它与需求册的区别是"需求说必须能做什么，契约说外部看到的具体形态"；与设计册的区别是"设计要求实现符合契约，但实现可重构，契约变更需公告"。混进任一侧都会重犯当前的错误。

> 若团队规模小、暂时不想维护三册，可**先分两册**：`requirements.md`（含契约章节，标注"稳定契约"）+ `design.md`（含全部实现细节）。契约独立成册作为后续演进。
